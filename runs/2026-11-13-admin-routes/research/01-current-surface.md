## 0. One-paragraph answer

A route today is a single `["vanity", name, pubkey, validUntil]` tag inside **one** app-key-authored kind-30000 event at `d=vanity-urls`. A name resolves to **a pubkey** — never to a page, a listing or a URL — and the path then renders as that person's page/profile. Absence of a name is not an error: the same path segment falls through to a **kind-30024 page authored by the app key at `d=<segment>`**. The only writer is a Lightning-paid purchase (`ZapPurchaseManager`), which appends to the registry server-side; the only management surface is a user-facing, ungated, own-name purchase page at `/dashboard/account/vanity-url`. **No admin or editor surface exists that names a route or points it at anything**, and there is no SDK publisher for the registry at all.

## 2. Expiry semantics

**What `validUntil` means.** An absolute UNIX timestamp in **seconds**, per entry, with no renewal chain and no owner-expiry concept. It is the only temporal field in the registry. **[S]** (`sdk/core/curation/vanityRead.ts:10` — `validUntil: number`; comment `sdk/config/vanity.ts:21` — `// Unix timestamp`)

**Who sets it — the server, and only the server.** On a validated zap receipt **[S]**:

- base = `now + validitySeconds` — `platform/server/ZapPurchaseManager.ts:187-188`
- if the same pubkey already holds the name and it has not lapsed, the new period is **added to the old expiry**, so early renewal does not lose time — `ZapPurchaseManager.ts:190-193`
- `validitySeconds` comes from the pricing tier matched by *highest qualifying amount* — `ZapPurchaseManager.ts:180`, `376-390`
- tiers: `6mo` 10 000 sats / 180 d, `1yr` 18 000 sats / 365 d, and in `NODE_ENV=development` only, `dev` 10 sats / 90 s — `platform/server/VanityManager.ts:47-55` **[S]**

The client never computes or sends `validUntil`. It sends `amountSats` and a signed zap request; the expiry is a server-side derivation from the payment (`platform/web/payments/zapPurchase.ts:70-81` → `platform/server/http/zapPurchase.ts:42-47`). **[S]**

**What happens on expiry — measured behaviour, and it is not "not found".**

1. The entry stops resolving: `resolveVanity` returns `null` when `entry.validUntil < now` (`sdk/core/curation/vanityRead.ts:62-64`; store equivalent `sdk/config/vanity.ts:140-142`; server equivalent `platform/server/ZapPurchaseManager.ts:245-250`). **[S]**
2. The store does not even hold it: seeding the client store **skips** expired entries (`sdk/config/vanity.ts:100-104`), and `getVanityForPubkey` requires `> now` (`vanityRead.ts:73`). **[S]**
3. The name becomes **claimable by anyone**: `isVanityAvailable` returns true when the incumbent's `validUntil < now` (`vanityRead.ts:44-54`; server `VanityManager.ts:149-158` and `validateRegistration` `ZapPurchaseManager.ts:91-93` — "already taken" is only raised for a *different* pubkey *still in date*). **[S]**
4. **The URL does not break; it changes meaning.** `/$vanityName` falls through to `StorefrontAddressPage` with the segment as the `d` tag (`platform/web/routes/$vanityName.tsx:30-41`), i.e. an expired vanity name silently becomes a request for the app key's kind-30024 page of that name, and renders "Nothing published yet" if there is none. No 404, no error, no notice that a name lapsed. **[S]** — see §4.
5. **Nothing sweeps.** There is no cron, timer or deletion path that removes an expired tag or republishes the registry. The tag survives in the published event until some *other* purchase triggers `publishRegistry` — and that publish writes `this.registry` unchanged (`ZapPurchaseManager.ts:404-405`), whose contents are only pruned at *ingest* (`ZapPurchaseManager.ts:100-104`). So between rebuilds, expired entries can be re-published indefinitely. **[S]**, with the consequence **[J]**: the registry is not self-cleaning, and "expired" exists only in readers' heads.

**What code enforces it.** Only readers, and only by returning null/skipping. The list, exhaustively: `sdk/core/curation/vanityRead.ts:53,63,73,82`; `sdk/config/vanity.ts:102,140,165,203`; `platform/server/ZapPurchaseManager.ts:101,241,248`; `platform/server/VanityManager.ts:91,157`. **[M]** (`git grep -n 'validUntil'`-derived; the files are quoted in full in evidence §4.)

**Judged consequence for this run [J]:** a route that has "no owner to expire" cannot inherit this field meaningfully. `validUntil` is a *rent* on a name, paid by a person, and its expiry is what makes the name re-claimable. If a managed route carries the same field, expiry must mean something else (or nothing — `0`/absent = permanent) and the resolution code must distinguish "no such route" from "route lapsed", because today the lapsed case is indistinguishable from the unowned-page case and silently changes what the URL renders.

## 4. How a name resolves to something renderable today

`platform/web/routes/$vanityName.tsx` is a **top-level** route, `id: '/$vanityName'`, a sibling of `/`, `/dashboard`, `/products` (`platform/web/routeTree.gen.ts:74-76`, `298`) **[M]**. TanStack Router gives static segments priority, so a registered name can never shadow a real route — the reserved list (`sdk/config/vanity.ts:51-89`) is belt-and-braces. A test pins the single-segment contract: `/some-vanity-name` → `/$vanityName`, and `/profile/<hex>` is *not* captured (`platform/web/routes/sellerRoute.test.tsx:52-64`) **[M]**.

Resolution order, exactly **[S]**:

```
0. router matches /:seg                      routeTree.gen.ts:74-76
1. gate: store.isLoaded?                     $vanityName.tsx:15, 25-27
      no  -> <LoadingState>                  (permanent if the read never lands — see below)
2. vanityActions.resolveVanity(seg)          $vanityName.tsx:19-22
      hit + not expired ->
         StorefrontOrProfilePage(pubkey)     $vanityName.tsx:30-31
            a. if the pubkey is not hex, resolve npub/NIP-05 -> hex
                                             StorefrontOrProfilePage.tsx:33-40
            b. fetch (pubkey, kind 30024, d='storefront-page')
                                             StorefrontOrProfilePage.tsx:42
            c. render it if parsed && enabled && content.length>0
                                             StorefrontOrProfilePage.tsx:63-65,
                                             storefrontQuery.ts:150-154
            d. else <ProfilePage profileId>   StorefrontOrProfilePage.tsx:67
      miss OR expired ->
3. StorefrontAddressPage(dTag = seg)         $vanityName.tsx:34-41
      author = appPublicKey from /api/config, kind 30024, d = seg
                                             StorefrontAddressPage.tsx:30-33
      a. config/page loading -> LoadingState  StorefrontAddressPage.tsx:38-40
      b. relay/transport error -> ErrorState + retry
                                             StorefrontAddressPage.tsx:42-52
      c. parsed && enabled && content>0 -> StorefrontRenderer
                                             StorefrontAddressPage.tsx:54-56
      d. absent / disabled / zero-block / unparseable -> EmptyState
         "Nothing published yet"             StorefrontAddressPage.tsx:58-67
```

**The fallbacks, stated as a rule:** a single path segment is resolved twice, in order — *rented name → person*, then *app-key page at that literal `d`*. There is **no 404 and no error state anywhere** in this path; the terminal state is always either a rendered page, a profile, or the deliberate empty state. **[S]**

Three consequences a managed route table must not inherit silently **[J]**:

- **A lapsed or unknown name is not "absent"** — it is reinterpreted as an app-key page address. Adding a route that points at a page and a route that points at a person means the two meanings of a segment now have to be ordered deliberately, and this file is where they already collide.
- **The empty state is indistinguishable from the negative paths.** "No route", "route points at a switched-off page", "route points at unparseable content" all render the same sentence (`StorefrontAddressPage.tsx:58-67`; `shouldRenderStorefrontPage` collapses `!enabled`, `content.length===0` and parse failure into one boolean, `storefrontQuery.ts:150-154`). Requirement §"a route naming an unparseable, switched-off or empty document must not blank the site" is satisfied *today* by that collapse — but it also means the site cannot tell the maintainer *why* a route shows nothing.
- **The `isLoaded` gate can hang.** `isLoaded` is only set by `setVanity` (`sdk/config/vanity.ts:116`), which only runs when `useVanitySettings` resolves; that query is `enabled: !!appPubkey` (`vanityBinding.ts:123`), and `appPubkey` comes from `/api/config`. With no app key configured the query is disabled, `setVanity` never runs, and `/$vanityName` renders `LoadingState` forever (`$vanityName.tsx:25-27`). **[S]** — a pre-existing edge, not caused by this run, but a route editor must not be built on top of it without noticing.

### The two coordinates the order names (premise check)

- Home: `platform/web/routes/index.tsx:57` — `useStorefrontAddressPage(APP_PUBKEY, 'home')` **confirmed verbatim at that line** **[M]**. The fallback composition below it is the inline constant at `index.tsx:81-101` (`Search`, one `ProductRow` with a single hard-coded `productDTags`, `Categories` with three entries), used when the published page does not resolve (`index.tsx:102`) **[S]**. Additional finding: `APP_PUBKEY` is a **hard-coded 64-hex literal at `index.tsx:48`**, not read from `/api/config` — so the home's author is pinned in source, and a config change would silently orphan it.
- Storefront publish: `platform/web/storefront/storefrontPublish.ts:60` — `const tags: string[][] = [['d', STOREFRONT_PAGE_D_TAG]]` **confirmed verbatim at that line** **[M]**, with the author explicitly documented as the logged-in user and *not* the app key (`storefrontPublish.ts:15-18`, enforced at `storefrontPublish.ts:86-90`) **[S]**. `STOREFRONT_PAGE_D_TAG = 'storefront-page'` from `@sdk/commerce/storefront/storefrontPage` — one fixed `d` for every author, so a user's page address is `(their pubkey, 30024, 'storefront-page')` and a *named* page for them does not exist.

So the order's §"Why this is the unblocker" holds as measured: `d='home'` under the app key and `d='storefront-page'` under the user's key are different coordinates, and nothing writes the former.

## 6. The admin/editor gating as it is now

### Client side

- **Reads.** Two kind-30000 lists from the app relay: `buildCurationListFilter('admins'|'editors', appPubkey)` → `{kinds:[30000], authors:[appPubkey], '#d':['admins'|'editors']}` (`sdk/core/curation/curationRead.ts:65-68`; d-tags at `curationLists.ts:8-9`) **[S]**.

- **Decision functions.** `isAdmin = adminSettings.admins.includes(pubkey)` (`curationRead.ts:148-151`); `isEditor = editorSettings.editors.includes(pubkey)` (`:158-161`); `isOwner = adminSettings.owner === pubkey` (`:153-156`); role precedence `owner > admin > editor > user` (`:270-274`) **[S]**.
- **Owner derivation.** `parseAdminSettings` sets `owner: admins[0] || appPubkey` — **the owner is whoever is first in the admin list**, falling back to the app key when the list is empty (`curationRead.ts:74-78`) **[S]**. That is a positional convention, not a stored field; reordering `p` tags changes the owner.
- **Composition.** `useUserRole` returns `{amIAdmin, amIOwner, amIEditor, userRole, isLoading}` from one call (`appSettingsQuery.ts:194-216`) — every dashboard surface gates off this hook **[S]**.
- **Route guard + nav.** `useRootRedirects.ts:28-43` redirects a non-admin away from `/dashboard/app-settings`; the nav is filtered by `adminOnly` with `isAdminLoading` treated as "show everything" (`ui/nav/model.ts:260-272`, wired at `platform/web/routes/_dashboard-layout.tsx:100`) **[S]**.

| `setup` | kind 31990 + content contains `"name":` | app key **or** admin, or anyone in bootstrap mode (`:50-61`) |
| `adminList` / `editorList` | kind 30000 + `d` = `admins` / `editors` | **admin only** (`:63-72`) |
| `blacklist` | kind 10000 | **admin or editor** (`:74-83`) |
| `general` | everything else | **admin only** (`:85-94`) |

So today **an editor cannot write anything through the proxy except the blacklist**, and any route-editor write over the WS path would be admin-only unless the validator is changed or a new server-side path is added. **[S]** + **[J]**

Every accepted event is **re-signed with the app key** before it is republished (`EventHandler.ts:236-238`; `platform/server/websocket.ts:30-46`), after `verifyEvent` checks the sender's signature **[S]**. That is why the stored admin list's `pubkey` is the app key, matching the `authors:[appPubkey]` read filter.

### Is the admin list an event, app config, or something else?

**It is an event** — kind 30000, `d=admins`, `p` tags, author = app key in storage — with two non-event seeds **[S]**:

1. at boot the server reads the newest kind-31990 app-settings document and adds its JSON `ownerPk` to the admin set (`platform/server/NDKService.ts:41-68`, specifically `:56-58`);
2. the server's own initial list is the config field `adminPubkeys`, and `startup.ts:71` passes **`adminPubkeys: []`** — physically empty **[M]**.

The effective set is then *replaced wholesale* by the newest `d=admins` event, both at boot (`NDKService.ts:69-83`) and live (`NDKService.ts:110-117`), via `updateFromEvent` which clears and re-adds from `p` tags (`platform/server/AdminManager.ts:26-39`; editors identical at `EditorManager.ts:26-39`) **[S]**. Consequence **[J]**: `admins[0]` is the owner client-side while `ownerPk` from app-settings seeds the server-side set — two different notions of "first/owner" that agree only if the publisher keeps the owner first. A route table gated on "admin or editor" inherits that ambiguity.

### The trust question the order flags, measured

The order says: *"the existing registry is authored by the app key; an admin acting on the app's behalf is a different trust question."* Measured, that is exactly right, and sharper than stated:

- the app key is a **server-side secret** (`EventSigner` is constructed from `APP_PRIVATE_KEY`, `platform/server/EventSigner.ts:10-14`, `EventHandler.ts:72`) and never reaches the browser;
- an admin's write reaches the app key **only** through the WS proxy, which re-signs whatever it validated (`websocket.ts:35-46`) — so "admin writes a registry entry" is not the admin signing a registry, it is the admin *asking the app to sign one*;
- the existing registry has **no** such path (W5 is unused and unvalidated), and the app-key signature today means only "the server computed this from a payment" (`ZapPurchaseManager.ts:187-202`). **[S]**
