## 1. Every consumer of a resolved route

Today "resolution" produces a **pubkey** (`sdk/config/vanity.ts:133-145`) or, for the home, a
**hardcoded `(APP_PUBKEY, 'home')` pair** (`platform/web/routes/index.tsx:57`). A typed target changes
what each of these receives. Ordered by how much moves.

### 1.1 The resolver itself

**C1 — `sdk/config/vanity.ts:133-145` `vanityActions.resolveVanity` (read-source).**
The whole name→pubkey rule, including expiry:

```
133	resolveVanity: (vanityName: string): VanityEntry | null => {
134		const { entries } = vanityState.get()
135		const entry = entries.get(vanityName.toLowerCase())
137		if (!entry) return null
140		if (entry.validUntil < Math.floor(Date.now() / 1000)) {
141			return null
142		}
144		return entry
```

Reads: a `Map<string, VanityEntry>` keyed by lowercased name. Changes: the entry gains a typed target
and (per the ACL ruling) an owner tier; the return type stops being enough for a renderer to decide
what to draw, because a pubkey cannot distinguish "profile", "page address" and "listing".
Note the shape is `{vanityName, pubkey, validUntil}` (`sdk/core/curation/vanityRead.ts:7-11`) — there is
no field for a target *kind* anywhere in the read layer either.

**C2 — `sdk/config/vanity.ts:95-118` `setVanity` (read-source).** The only writer of resolved entries:
it drops expired rows at `102-104` (`if (entry.validUntil < now) continue`) and builds
`entries` + `pubkeyToVanity` (the reverse index). A typed target means this projection changes; the
reverse index (`pubkey→name`) only makes sense for profile-targeted routes and is read by the builder
(C16).

**C3 — `sdk/core/curation/vanityRead.ts:5,7-11,31-35` the wire format (read-source).**
`VANITY_REGISTRY = { kind: 30000, dTag: 'vanity-urls' }`; entries are
`["vanity", name, pubkey, validUntil]` and `readVanityEntries` *silently drops* any tag missing one of
the four (`:33`). A target type must either fit inside `pubkey` or extend the tag array — and extending
it is invisible to this filter, which would then drop nothing but also parse nothing new.

**C4 — `sdk/core/curation/vanityRead.ts:56-65` `resolveVanity` (framework-free twin) (read-source).**
Duplicates C1's expiry semantics against `VanitySettings` (not the store). Two resolvers with the same
name and different inputs is the drift risk for a typed target: **both** must learn the target, or the
route (C1) and any workflow/server caller (C4) disagree.

**C5 — `platform/web/config/vanityBinding.ts:81` re-exports + `:95-128` `useVanitySettings`
(read-source).** The relay read of the registry (`readVanitySettingsWorkflow`) plus a live
`ndk.subscribe` that invalidates `configKeys.vanity(appPubkey)` on every event (`:100-118`). Consumers
that switch from the store to `useVanityState` land here — `vanityBinding.ts:16-18` states the route
"still reads the temporary `vanityStore` adapter… consumers migrate to `useVanityState` lazily".

**C6 — `platform/web/config/vanityStore.ts:27-28` (read-source).** The `@tanstack/store` mirror the
route actually reads; file header `:12-14` marks it TEMPORARY, deleted when call sites are rewired.
A new management surface must not add a third reader of this adapter.

**C7 — `platform/web/app/useVanitySync.ts:12-19` (read-source).** The app-level drain
`useVanitySettings(config?.appPublicKey)` → `vanityActions.setVanity(...)`, i.e. the only place the
route's data comes from at runtime. If a typed target is read through a *different* query, the route and
the sync can hold different generations of the table.

### 1.2 The routes

**C8 — `platform/web/routes/$vanityName.tsx:19-22` (read-source).** The only consumer of C1:

```
19	const resolvedPubkey = useMemo(() => {
20		const entry = vanityActions.resolveVanity(vanityName)
21		return entry?.pubkey ?? null
22	}, [vanityName, isLoaded, lastUpdated])
```

It discards everything except `pubkey`. Changes: return the whole target; the dependency array must
also carry whatever new field decides rendering.

**C9 — `platform/web/routes/$vanityName.tsx:30-32` (read-source).** `resolvedPubkey → 
<StorefrontOrProfilePage profileId={resolvedPubkey} />`. A target of type "storefront page address" or
"listing" cannot go through this component at all — it takes a *person identifier*.

**C10 — `platform/web/routes/$vanityName.tsx:41` (read-source).** The fallback, and the single most
important constraint on the whole design:

```
41	return <StorefrontAddressPage dTag={vanityName} />
```

Every unmatched single segment is *already* a page address on the app key (HANDOVER-CMS-INTEGRATION
§6.1, quoted in the file header `:34-40`). So today there is no such thing as an unknown route name:
`/anything` resolves to `(app key, 'anything')` and renders the empty state. A route table therefore
does not sit on empty ground — its **name space is the same URL space as page addresses**, and the
lookup order (table first, app-key address second) is a compatibility decision, not a detail.

**C11 — `platform/web/routes/index.tsx:57-58` (read-source).** The default, hardwired:

```
57	const { data: homeResult } = useStorefrontAddressPage(APP_PUBKEY, 'home')
58	const publishedHome = shouldRenderStorefrontPage(homeResult) ? homeResult.page : null
```

Changes: `APP_PUBKEY`/`'home'` become "the route flagged default, resolved to its target"; `:111`
`<StorefrontRenderer page={page} pubkey={APP_PUBKEY} />` must pass the *target author*, not the app key,
for an admin-authored home to render with the right slots.

**C12 — `platform/web/routes/index.tsx:74-113` (read-source).** The inline fallback composition and its
selection at `:102`:

```
102	const page = publishedHome ?? (parseStorefrontPage(JSON.stringify(homePage)).page as never)
```

This is the fail-safe that a managed default must either keep or deliberately replace; it is also proof
that "no page" is already a *defined* state for `/`, not an error.

**C13 — `platform/web/routes/index.tsx:109,132` (read-source).** `navigate({ to: '/$vanityName', params:
{ vanityName: 'featured' } })` — the literal `'featured'` appears twice, in `BrowseNav` and
`BrowseIndexHost`. A route table makes these two literals the *only* hardcoded route names in the app;
they become either table lookups or a documented reserved name.

**C14 — `platform/web/routes/profile.$profileId.tsx:10` (read-source).**
`<StorefrontOrProfilePage profileId={profileId} />`. This route is a **target type**, not a resolver: a
`profile`-typed route can navigate here or render the same component directly, but the URL contract must
not double-resolve (a name that resolves to a profile must not also be reachable as `/profile/<name>`).

### 1.3 The render hosts and the storefront read

**C15 — `platform/web/storefront/StorefrontAddressPage.tsx:29-33` (read-source).** Takes **only**
`{ dTag }`; the author is *fixed* to the instance's own key:

```
30	const { data: config, isLoading: isLoadingConfig } = useConfigQuery()
31	const author = config?.appPublicKey ?? ''
32	const hasAddress = isValidHexKey(author) && dTag.length > 0
33	const { data: page, ... } = useStorefrontAddressPage(hasAddress ? author : undefined, dTag)
```

Changes: an optional `author`/target prop, because an admin-authored page lives at a different pubkey
and today the component physically cannot read it. Failure handling is already the model the rest should
copy: `:42-52` error + retry; `:58-67` absent / disabled / zero-block / unparseable → one deliberate
empty state.

**C16 — `platform/web/storefront/StorefrontOrProfilePage.tsx:33-40, 63-67` (read-source).**
Identifier→pubkey (`:33-40`), page read (`:42`), draft preview (`:43-51`), then
`shouldRenderStorefrontPage(...) → StorefrontRenderer`, else `<ProfilePage/>` (`:63-67`). Three layers of
fallback per ADR-0006 (header `:17-20`). Note there is **no `isError` branch** here — a transport failure
silently becomes the profile page, which is the opposite of C15's explicit error state.

**C17 — `platform/web/storefront/storefrontQuery.ts:150-154` `shouldRenderStorefrontPage`
(read-source).** The single render predicate, used at `index.tsx:58`, `StorefrontAddressPage.tsx:54` and
`StorefrontOrProfilePage.tsx:63`:

```
150	export function shouldRenderStorefrontPage(result: StorefrontPageResult | undefined): result is … {
153		return Boolean(result?.page?.enabled && result.page.content.length > 0)
154	}
```

Any "the default route's target failed" rule must be expressed **through this predicate or beside it**,
never as a second check in the new route component — otherwise the badge and the fallback can disagree
(see AGENTS.md:124-125 in §4).

**C18 — `platform/web/storefront/storefrontQuery.ts:128-141` `storefrontAddressPageQueryOptions`
(read-source).** Key `[...storefrontKeys.all, 'address', pubkey, dTag]` (`:130`), `enabled` on valid hex
+ non-empty `d` (`:132`). A new target type needs a key dimension (or its own query); reusing this key
for a different coordinate would collide in the cache.

**C19 — `platform/web/storefront/storefrontQuery.ts:75-102` `fetchStorefrontPage` (read-source).** Returns
a *result*, not a page; `EMPTY_RESULT` for invalid input (`:76`); re-checks author+`d` on the answers
(`:92-95`); `selectReplaceable` picks the newest (`:44-60`). The read is a bounded `fetch` justified in
a comment at `:78-80` — the sdk doctrine's one permitted shape for a single-entity read (§4).

**C20 — `platform/web/storefront/StorefrontBuilder.tsx:97-101` (read-source).** The producer that
*prints* a page's address:

```
 97	const { data: vanitySettings } = useVanitySettings(config?.appPublicKey)
 99	const vanityEntry = useMemo(() => getVanityForPubkey(vanitySettings, pubkey), [vanitySettings, pubkey])
101	const liveHref = vanityEntry ? `/${vanityEntry.vanityName}?preview=draft` : `/profile/${pubkey}?preview=draft`
```

If a page can be published to a *named* route, this string is wrong the moment the page is not at the
user's vanity name — it must come from the route table, or the editor reports an address that does not
render the page.

### 1.4 The management surface's own seams

**C21 — `platform/web/app/useRootRedirects.ts:24-44` (read-source).** The admin gate is a **literal path
prefix**:

```
26	const isAdminRoute = pathname.startsWith('/dashboard/app-settings')
40		if (isAdminRoute && !amIAdmin) {
41			navigate({ to: '/dashboard' })
```

So a management page mounted anywhere else is unguarded, and one mounted under that prefix is
admin-only by construction — which contradicts the ruling's "editor" tier (see §8). This is a consumer
of *route naming*, not of resolved routes, and it is the cheapest thing to get wrong.

**C22 — `ui/nav/model.ts:163-177` (read-source).** The `APP SETTINGS` section (`adminOnly: true`, every
item `adminOnly`), pinned exactly by `ui/nav/model.test.ts:22-60`. A new dashboard page must be added
here *and* to that expectation table, or the suite fails (that is the guard working).

**C23 — `platform/web/routes/_dashboard-layout/dashboard/account/vanity-url.tsx:234-244`
(read-source).** The self-serve vanity surface prints `${window.location.origin}/${vanityName}` and an
`<a href={`/${vanityName}`}>`. Same class as C20: a URL string that must be produced by the new table.
Its expiry display (`:113-150`, `formatExpiration` → `daysLeft`/`isExpiringSoon`) is the **only**
"warn before it lapses" surface that exists today (read-source).

**C24 — `platform/server/VanityManager.ts:86-94` (read-source).** The server-side write path, and the
only conflict rule in the codebase:

```
91	if (existing && existing.pubkey !== pubkey && existing.validUntil > Math.floor(Date.now() / 1000)) {
92		return `Vanity name already taken: ${key}`
```

Owner-vs-owner only; no notion of tier or of a route's kind. `:46-54` (`VANITY_PRICING`, sats→days) is
where "a reservation is a paid term" already exists in code.

**C25 — `platform/web/routeTree.gen.ts` (read-source).** Generated by `tsr generate`
(`package.json` `generate-routes`). Any new route file requires regeneration; the generated file lists
`/$vanityName` as the single-segment route (`:75-76`) and every dashboard path.

**C26 — `platform/web/app/routeComposition.test.ts:73-104` (read-source, guard).** Enforces "routes =
composition only": no route module imports another route module (`:73-81`), and the only export of a
route module is its own `Route` (`:83-104`). A route table therefore cannot live in
`platform/web/routes/` — it must live in `platform/web/app/`, `sdk/`, or a feature module.

## 3. Negative paths, and what decides each today

All five of the order's cases, plus the two transport asymmetries I found.

### N1 — a named route whose target does not resolve

Two different failures, two different outcomes, both silent (read-source):

- **name absent from the table** → `$vanityName.tsx:41` `<StorefrontAddressPage dTag={vanityName} />` →
  `(app key, '<segment>')` → empty state (`StorefrontAddressPage.tsx:60-67`, "No page has been published
  at this address"). Not a 404 — `platform/web/routes/` has no `notFoundComponent` (measured: grep for
  `notFound` in `__root.tsx`/`app/` returns nothing).
- **name present, target pubkey has no page** → `StorefrontOrProfilePage.tsx:63-67` → the **profile**,
  because the target was consumed as an identity, not a page.

Changing the target to a typed union makes case 2 expressible at all ("this route points at a page that
is not there"), and that state does not exist today.

### N2 — a route pointing at a page that is switched OFF

```
storefrontQuery.ts:153	return Boolean(result?.page?.enabled && result.page.content.length > 0)
```
`enabled:false` → predicate false → home: inline fallback (`index.tsx:102`); address page: empty state
(`StorefrontAddressPage.tsx:58-67`); profile: `ProfilePage`. Measured render assertion already exists for
the address page (`StorefrontAddressPage.test.tsx:108-115`).

### N3 — a page that parses to zero blocks

Same predicate, second conjunct (`result.page.content.length > 0`, `storefrontQuery.ts:153`), whose
docstring states the reason (`:143-149`: "an empty page is worse for a visitor than the profile they
expected"). Same three outcomes as N2.

### N4 — a route whose target is an unparseable document

`parseStorefrontPage` returns `{page: null, error}` → `page?.enabled` is `undefined` → predicate false.
`StorefrontAddressPage.tsx:25-27` documents the choice ("A page that fails to parse degrades to the same
empty state"); `StorefrontAddressPage.test.tsx:117-123` asserts it with `content: 'not json'`.
`storefrontQuery.ts:18-23` is the doctrine sentence: the result type exists so callers can tell "no page"
from "a page we could not read" — **but no consumer currently surfaces that distinction** (all three
collapse it). That is a gap the acceptance should close for a *named* route, where a visitor has a name
to complain about.

### N5 — the DEFAULT route removed, or its target fails

Nothing decides this today, because the default cannot be removed: it is the constant at
`index.tsx:57`, and the "fails" branch is the inline composition at `index.tsx:102`
(`publishedHome ?? parse(...)`). The nearest existing code is the predicate call at `:58`. So today:

- default target switched off / zero-block / unparseable → **inline composition** (never blank, measured
  by inspection of `:102`, and asserted indirectly by `navigation.spec.ts:6-9`).
- default route "removed" → not representable.

A managed default makes the removal case real, and the order (`order.md:70-74`) explicitly leaves the
answer open (inline composition vs honest empty state). The acceptance must pin whichever is chosen;
until then this is **UNVERIFIED by design**, not by oversight.

### N6 (found, not asked) — transport failure is asymmetric

- address page: explicit error + retry (`StorefrontAddressPage.tsx:42-52`, `retryTestId`
  `storefront-address-retry`).
- profile/page route: no `isError` branch (`StorefrontOrProfilePage.tsx:26-68`) → falls to `ProfilePage`
  as if the author had no page (`storefrontQuery.ts:70-73` says relay failures are *allowed to reject*
  precisely so React Query shows `isError` — the profile host does not consume it).
- home: `index.tsx:57-58` reads `data` only; `isError` is dropped → the inline composition.

A new route component must pick one of these three behaviours and say so.

## 4. Acceptance matrix, and what the doctrine requires of new code

### 4.1 Matrix — what must be asserted per affected surface

| # | surface | must assert | negative states that must be asserted too |
| --- | --- | --- | --- |
| A1 | `/` (default) | resolves the default route's target and renders it through `StorefrontRenderer` with the **target author** as `pubkey` | target absent / off / zero-block / unparseable → the chosen fallback (inline or empty), never blank; admin-gated authoring |
| A2 | `/<name>` → storefront page | address target renders through the ported renderer | same four, plus transport error → visible error + retry |
| A3 | `/<name>` → profile | `StorefrontOrProfilePage` path unchanged (page if enabled, else `ProfilePage`) | unparseable/off → `ProfilePage`, never an error |
| A4 | `/<name>` → listing / external URL (if admitted) | the target type renders, or is refused at *write* time, not at read | an unknown/unsupported target type must not render a blank route |
| A5 | `/<name>` not in the table | today's app-key address-page behaviour is preserved (compat) **or** deliberately replaced — asserted either way | empty state must remain token-clean and not an error (`StorefrontAddressPage.tsx:58-67`) |
| A6 | `/profile/<id>` | unchanged: real `routeTree` resolves it and `/$vanityName` does not capture it (`sellerRoute.test.tsx:41-64`) | npub/nprofile/NIP-05 identifiers still resolve (`:66-74`) |
| A7 | dashboard management page | mounts under the admin gate, lists/adds/removes/modifies, shows the app-key/trust model | non-admin refusal, empty table, save failure, conflict on a taken name |
| A8 | producer surfaces | `StorefrontBuilder` live href and the vanity page's printed URL come from the table (C20, C23) | a page with no route must not print a URL that 404s or renders nothing |
| A9 | nav | the new page appears in `DASHBOARD_NAV` exactly once, admin/editor-appropriate (`ui/nav/model.ts:163-177`) | `ui/nav/model.test.ts` expectation updated in the same change |

### 4.2 Doctrine that binds any new code (quoted)

**Read seam — `sdk/AGENTS.md:42-55`** (the order attributes this to the root `AGENTS.md`; see §7):

```
42	- **`EventReadContext.stream(filters)` is the default read path.** Opening it is synchronous; events are
46	- **Use `stream` for anything list-based or live** — browse/home, search results, category rows, bids and
48	- **`EventReadContext.fetch(filters)` is a bounded stream**, implemented _over_ `stream` … It is
49	  justified **only** for a single-entity/detail read where holding a stream is not warranted — own profile,
54	- **Every `fetch` carries a one-line justification comment naming the case**; reviewers flag `fetch` in any
55	  list/live context.
```

Consequence for the change: **reading the route table is a single-entity/detail read** (one coordinate:
app key, kind 30000, `d=vanity-urls`) — so `fetch` is the correct class and needs the one-line comment,
exactly as `storefrontQuery.ts:78-80` does. **A list of routes for the dashboard is list-shaped** and must
use `stream`, not `fetch`. Getting this backwards is the most likely doctrine violation in the whole
change.

**Placement — `sdk/AGENTS.md:7-20`.** "Place a module by what it _is_… If a module carries a marketplace
noun it is not `core/`." A route table is instance configuration with a marketplace noun (routes to store
pages), so it belongs in `sdk/config/` or `sdk/commerce/` — not a new `sdk/core/routes` (judged from the
table; the existing `sdk/commerce/curation` is already a recorded debt row, `sdk/AGENTS.md:31-34`).

**`ui/` ↔ `platform/` boundary — `ui/AGENTS.md:20-31`:**

```
20	`ui/boundary.test.ts` fails the build if any file under `ui/` imports:
22	- `@/…` (the legacy host)
23	- `@platform/…`
24	- `- @tanstack/…`
25	- `@nostr-dev-kit/…`
30	`@sdk/…` type and workflow imports are permitted.
```

and `ui/AGENTS.md:33-41`: "A component is a **pure function of props**… No store subscriptions, no query
hooks, no `fetch`, no routing, no signing, no publishing", and `ui/AGENTS.md:120`: "**No data fetching.**
No `fetch`, no `useQuery`, no `useStore`."

Consequence: the management table's rows/forms are `ui/` views taking props; the resolve/validate/save
calls, the query hooks and the route-param parsing stay in `platform/web/`. A "route row" that fetches
its own target is a boundary violation.

**Routes are composition only — `platform/web/routes/AGENTS.md:26-32`:** "Keep data fetching in query
hooks or route loaders and publishing in `src/publish/`; avoid embedding protocol construction in route
components… Preserve loading, empty, error, and stale states for relay-backed pages." Enforced
mechanically by `routeComposition.test.ts:73-104`.

**One predicate for gate and notice — `AGENTS.md:124-125`:** "**The gate and the notice read the same
predicate**, so a badge can never disagree with the reason an item is missing from a feed." Applied here:
`shouldRenderStorefrontPage` (C17) is that predicate; a route that is refused must state *why* from the
same value that suppressed it, not from a second check.

**Direct navigation must say what failed — `AGENTS.md:110-115`:** "**Direct navigation still resolves the
event** (by id, by coordinate) and states _which_ constraint failed. A silent disappearance, or a bare
'not found' for an event that exists on the relay, is not an acceptable outcome." Today a named route
collapses absent/off/empty/unparseable into one empty state (N1–N4) — defensible for a typo'd URL,
**not** for a route an admin deliberately published. This is the strongest existing argument for a
distinguished failure state on named routes (judged, quoting the rule verbatim).

**No new event kinds without code+tests+docs — `AGENTS.md:63-64`:** "No new event kinds, payment
semantics, relay assumptions, or network egress paths without code, tests, and documentation that make
the decision explicit." If the resolution rule stays inside kind 30000/`d=vanity-urls`, nothing new is
introduced; a second registry kind would be a new event kind and owes all three.

**Feature Quality Gate — `AGENTS.md:172-189`:** every feature PR includes "a targeted Playwright E2E
test… with video recording enabled", following the Test Isolation rules (`AGENTS.md:135-146`, no external
network). So the acceptance is **not** satisfied by unit + component tests alone.

## 8. APPENDED — ACL ruling (`runs/2026-11-13-admin-routes/ruling-acl.md`), folded in

Added after the ruling was written. It changes the acceptance surface in two ways: resolution now carries
**who may touch a path**, and expiry becomes **the reservation term** rather than an obstacle
(`ruling-acl.md:28-31`). Nothing below changes §1–§7; it extends §4.1 and §3.

### 8.1 The five negative paths, and what decides each today

**A1 — an editor touches a path NOT in their grant → refused, and the refusal is a VISIBLE state, not a
silent no-op.**
Nothing decides it. Measured: the only role surface is `useUserRole`
(`platform/web/app-settings/appSettingsQuery.ts:194-210`) returning `amIAdmin / amIOwner / amIEditor` as
three booleans — **no path dimension anywhere**. The only path-scoped control in the app is the literal
prefix `pathname.startsWith('/dashboard/app-settings')` (`platform/web/app/useRootRedirects.ts:26`), which
is all-or-nothing for admins. Refusal today would be a silent no-op by construction (the write would simply
not happen) — exactly the failure mode the ruling forbids.
*What must be built:* a per-path grant predicate on the route entry + rendered refusal. The **visible**
half already has a house component: `SettingsAccessDenied` (`ui/settings/operator-settings-views.tsx:59`,
already used at `dashboard/app-settings/team.tsx:211`, `blacklists.tsx:240`, `featured-items.tsx:590`, and
already covered by `ui/settings/operator-settings-views.test.tsx:9`), which is the right escalation level
per `ui/AGENTS.md:218-221`.
*Test:* new `sdk/core/curation/routeAcl.test.ts` (**unit** — grant predicate: in-grant / out-of-grant /
admin override), new `platform/web/.../managedRoutes.test.tsx` (**component render** — the refusal is
rendered, not swallowed), and `e2e/tests/managed-routes.spec.ts` (**e2e** — an editor session gets the
refusal state on an un-granted path).

**A2 — a premium user requests a path already held by an admin or editor route → refused, with the reason
stated.**
Partly decided, and the part that is decided is **tier-blind**. Measured, `platform/server/VanityManager.ts:86-94`:

```
91	if (existing && existing.pubkey !== pubkey && existing.validUntil > now) {
92		return `Vanity name already taken: ${key}`
```

— an owner-vs-owner check in the server write path, mirrored client-side by
`vanityActions.isVanityAvailable` (`sdk/config/vanity.ts:150-166`), which checks reserved words, format and
expiry but knows nothing of admin/editor routes. So: a name held by an **admin route** that is not in the
vanity registry is not seen at all, and a name held by an **editor grant** (which has no event) cannot be
seen either. The reason string exists but cannot name the holder's tier.
*Constraint:* the client and server predicates must stay literal-equal or they drift — the same
"gate and notice read the same predicate" rule (`AGENTS.md:124-125`).
*Test:* new `platform/server/VanityManager.test.ts` (**unit** — there is no test for this file today,
measured), extending `sdk/core/curation/curationRead.test.ts:265-276` (**unit**) for the client mirror, and
`e2e/tests/managed-routes.spec.ts` (**e2e** — the reason is visible to the requester, not just a toast).

**A3 — a reservation used AFTER its `validUntil` → no longer resolves, and the holder is warned BEFORE it
lapses.**
Resolution is **decided**, the warning is **not**. Measured:
`sdk/config/vanity.ts:140-142` returns `null` on `validUntil < now`; `setVanity` drops expired rows at
`:102-104`; the read layer does the same (`sdk/core/curation/vanityRead.ts:63`). So it stops resolving —
but the *observable* result is `$vanityName.tsx:41` → app-key address page → "Nothing published at this
address": the holder and their customers see an unrelated empty state, with no statement that a
reservation lapsed.
Warn-before-lapse exists only as display code on the self-serve vanity page:
`formatExpiration` → `daysLeft` / `isExpiringSoon` (`vanity-url.tsx:113-150`) driven by
`getExpiredVanityForPubkey` (`sdk/core/curation/vanityRead.ts:76-83`). There is **no** notification, no
banner on the dashboard beyond that page, and no grace window (the ruling leaves the grace question open,
`ruling-acl.md:49-51`).
*Test:* `sdk/core/curation/curationRead.test.ts:265-276` (**unit** — the lapse boundary, `'old'` already
pinned at `:273`), `platform/web/storefront/...` (**component render** — the lapsed route's state names the
lapse instead of the generic empty state), `e2e/tests/managed-routes.spec.ts` (**e2e** — seed an expired
reservation and assert the holder-facing warning precedes the lapse in the dashboard).

**A4 — an admin removes another tier's route → takes effect, and the affected holder is informed.**
Nothing decides it: **there is no removal path at all**. Measured: no module under `platform/web/` writes
kind 30000/`d=vanity-urls` — the only writer is the server's zap-purchase flow
(`platform/server/VanityManager.ts:60-94` via `EventHandler.ts:76`), which only ever *adds or renews* its
own paid entries. "Full control over the app and its pages" (`ruling-acl.md:13-16`) therefore has no
mechanism behind it yet; the "informed" half has no notification producer for routes.
*Test:* `sdk/core/curation/routeAcl.test.ts` (**unit** — an admin removal is authorized over any tier, and
the removal is recorded so the holder can be told), new `managedRoutes.test.tsx` (**component render** —
the holder's "this route was reassigned" state), `e2e/tests/managed-routes.spec.ts` (**e2e** — admin removes,
holder's dashboard shows it).

**A5 — the DEFAULT route is held by a reservation that LAPSES → `/` must NOT blank; it falls back.**
Nothing decides it, and it cannot happen today: the default is the constant
`useStorefrontAddressPage(APP_PUBKEY, 'home')` (`platform/web/routes/index.tsx:57`), which no reservation can
occupy. The fallback that *must* be reused is the one already on the page:
`index.tsx:102` `publishedHome ?? parseStorefrontPage(JSON.stringify(homePage)).page`, gated by
`shouldRenderStorefrontPage` at `:58` (C17). So the mechanism to satisfy the ruling exists; what is missing
is that the default becomes data and the lapse reaches that expression. The ruling also makes this a
*ranking* question — when a lapsed reservation vacates the default, the next candidate is ambiguous
(`ruling-acl.md:47-51`).
*Test:* new `platform/web/routes/homeDefault.test.tsx` (**component render** — default route lapses → the
inline composition renders and the page is non-empty; there is **no** test for `routes/index.tsx` today,
measured), `platform/web/storefront/storefrontQuery.test.ts:256-290` (**unit** — the predicate the fallback
hangs on), `e2e/tests/navigation.spec.ts:6-9` (**e2e** — the cheapest "did `/` blank" net), plus
`e2e/tests/managed-routes.spec.ts` for the seeded-lapse case.
